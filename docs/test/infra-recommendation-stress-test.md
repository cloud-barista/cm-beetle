# 컴퓨팅 인프라 추천 엔진 대규모 스트레스 테스트 및 병목 분석

- **작성일**: 2026-11-13
- **대상 범위**: `POST /beetle/recommendation/infra` (`pkg/core/recommendation`, `pkg/api/rest/controller`, `pkg/core/common`)
- **테스트 환경**: `CM-Beetle` (`HEAD`), `CB-Tumblebug` (`v0.13.8`), `CB-Spider` (Docker Compose 로컬 연동, 호스트 메모리 `15 GiB` / 가용 `8.8 GiB`)
- **타겟 클라우드**: `aws` / `ap-northeast-2` (`limit=3`, `minMatchRate=85.0`)

---

## 1. 테스트 목적 및 배경

수백 대에서 천 대 규모의 온프레미스 서버 모델을 단일 요청으로 타겟 클라우드 인프라로 추천(`POST /beetle/recommendation/infra`)할 때의 **선형 확장성, 하위 호출(`Sub-Request`) 병목 구간, 메모리(`RSS`) 사용 추이 및 실운영 한계 지점**을 정량적으로 파악하기 위해 추천 단독 스트레스 테스트를 수행했습니다.

특히 클라이언트 측의 짧은 타임아웃(`2~3분`)으로 인한 조기 종료와 실제 시스템 장애(에러 응답, Rate Limit, OOM 등)를 명확히 구분하기 위해 다음 타임아웃 구성을 사전 검증한 후 측정을 진행했습니다.

- **CM-Beetle REST 서버 (`pkg/api/rest/server.go`)**: Echo 기본 `http.Server` 설정(`ReadTimeout = 0`, `WriteTimeout = 0`)으로 서버 측 강제 연결 종료 없음
- **CB-Tumblebug 클라이언트 (`pkg/client/tumblebug/client.go`)**: 개별 하위 API 호출당 타임아웃 `50분` 및 `HTTP 429` 발생 시 자동 재시도(`최대 3회`) 적용
- **벤치마크 클라이언트**: 단계별 요청 타임아웃을 `2시간`(`120m`)으로 설정하고 TCP Keep-Alive(`30s`)를 활성화하여 클라이언트 타임아웃 간섭을 완전히 배제

## 2. 테스트 워크로드 및 관측 구성

### 2.1 합성 온프레미스 인프라 모델 (`OnpremInfra`)

실제 엔터프라이즈 4-Tier 구성을 모사하여 노드 수(`N`)에 비례하는 유효 `OnpremInfra` 페이로드를 결정론적 시드(`seed=20261113`)로 생성했습니다.

- **역할군 및 방화벽 정책 (4종 순환 배치)**:
  - `web` (`TCP 22, 80, 443`), `was` (`TCP 22, 8080, 8443`), `db` (`TCP 22, 3306, 5432`), `worker` (`TCP 22, 9092`) -> 보안 그룹 중복 제거 시 총 `4개`의 `SecurityGroup`으로 압축되는지 함께 검증
- **하드웨어 및 OS 프로파일 조합**:
  - `vCPU`: `2, 4, 8` Threads / `Memory`: `4, 8, 16, 32 GB` / `RootDisk`: `30, 50, 100 GB` (`SSD`)
  - `OS`: `Ubuntu 22.04.5 LTS` (`x86_64`)
- **네트워크 토폴로지**:
  - 단일 사설 대역(`10.1.0.0/16`) 내에서 `240대` 단위로 `/24` 서브넷(`10.1.1.0/24` ~ `10.1.5.0/24`)과 게이트웨이를 자동 분할 배치

### 2.2 실시간 관측 지표

각 요청에 고유 `X-Request-Id` 헤더를 부여하고, 실행 중 **30초 주기**로 다음 지표를 수집했습니다.

1. `GET /beetle/request/{reqId}?brief=true` 조회를 통한 실시간 `subRequestSummary` (`total`, `handling`, `success`, `error`)
2. 호스트 `/proc/<pid>/status` 기반 컨테이너별 물리 메모리 점유량(`VmRSS`: `cm-beetle`, `cb-tumblebug`, `cb-spider`)
3. 최종 응답의 HTTP 상태 코드, 페이로드 크기, 추천된 `NodeGroup` 수(`validVMs / N`), 서브넷 분할 수 및 보안 그룹 중복 제거 결과

## 4. 병목 원인 및 실운영 시스템 한계 지점 진단

### 4.1 핵심 속도 병목: 동일 프로파일에 대한 중복 순차 API 호출 (`5N` 구조)

- 현재 `RecommendInfraCandidates`는 노드 배열(`srcInfra.Nodes`)을 순차 순회하며 매 노드마다 `RecommendNodeSpecs`(`1회`), `RecommendVmOsImages`(`1회`), 후보별 `PreflightCheckCspProvisioning`(`limit`회, 기본 `3회`)을 호출합니다.
- 온프레미스 서버가 `1,000대`여도 실제 고유 하드웨어/OS 조합(`vCPU, Memory, Disk, OS`)은 십수 종 이내인 경우가 대부분이지만, 요청 범위 캐시(Memoization)가 없어 전체 지연 시간의 **80%(`16분`)**가 동일한 스펙/이미지 카탈로그 검색을 반복하는 데 소비됩니다.

### 4.2 실운영 한계 지점 1: 프록시 및 웹 구간 동기 타임아웃 (`약 105~110대` = `2분` 경계)

- `CM-Beetle` 프로세스 자체는 동기 연결을 끊지 않더라도, 실제 운영 환경의 앞단 게이트웨이(Nginx 기본 `60s`, AWS ALB / Cloudflare `100~120s`, Next.js API Rewrite 프록시 `120s`)는 응답 헤더가 `2분` 내에 오지 않으면 `502/504 Gateway Timeout`으로 연결을 종료합니다.
- 실측 기준 **`100대`가 `1분 54.5초`**이므로, 동기(`Synchronous`) 호출 방식에서는 **약 `105~110대`가 사용자 웹/프록시 환경의 실질적인 상한선**이 됩니다.

### 4.3 실운영 한계 지점 2: 대규모 반복 요청 시 메모리(`RSS`) 거동 및 OOM 임계 추정

`100대`부터 `1,000대`까지 누적 `5,500대`(`27,500회` 하위 호출)를 처리하는 동안 각 컴포넌트의 메모리 거동은 다음과 같이 뚜렷한 차이를 보였습니다.

1. **`cb-spider` (`97.9 ~ 102.4 MB` 고정)**:
   - 캐시된 메타데이터 및 경량 호출 위주로 동작하여 `1,000대`까지 메모리 증가가 전혀 없었습니다.
2. **`cb-tumblebug` (`160 MB ~ 최대 939.6 MB` 주기적 톱니 파형)**:
   - 노드 수(`N`)에 비례하여 무한 증가하지 않고, 리전 전체 스펙/이미지 목록 직렬화 버퍼가 약 `900 MB` 부근에 도달할 때마다 Go GC가 동작하여 `160 ~ 300 MB` 수준으로 정상 회수되었습니다. 단, `cb-tumblebug` 컨테이너 메모리를 `1 GB` 이하로 제한한 환경에서는 대규모 추천 시 OOM이 발생할 수 있으므로 최소 `2 GB` 이상의 여유 메모리가 권장됩니다.
3. **`cm-beetle` (일시 피크 `+0.30 MB/노드` 및 `lkvstore` 상주 누적 `+27 MB/1,000노드`)**:
   - 단일 요청 처리 중 피크 RSS는 `100대 139.6 MB -> 500대 281.3 MB -> 1,000대 509.2 MB`로 노드당 약 `0.30 MB`씩 선형 증가합니다.
   - 요청 종료 및 GC 이후의 베이스라인 RSS 역시 초기 `85.2 MB`에서 `1,000대` 진입 직전 `208.0 MB`(`4,500대` 누적 처리 후 `+122.8 MB`)로 계단식 상승했습니다. 이는 `ResponseBodyDump` 미들웨어와 `lkvstore`(`sync.Map` 기반 인메모리 저장소)가 완료된 모든 요청의 본문, 응답 데이터, `5N`개 `SubRequest` 배열을 메모리에 영구 유지하기 때문입니다.

## 5. 고도화 제안 (개선 로드맵)

사용자 대기 시간이 `2분`(`약 100대`)을 넘어가는 대규모 인프라 추천을 안정적이고 빠르게 지원하기 위해 다음 3단계 고도화를 권장합니다.

### 5.1 대규모 추천의 비동기(`Prefer: respond-async`) 기본 전환 및 UI 연동

- **현황**: `CM-Beetle` 백엔드 컨트롤러(`pkg/api/rest/controller/recommendation.go`)에는 이미 RFC 7240 기반 `Prefer: respond-async` 비동기 실행(`202 Accepted` 반환 및 `GET /beetle/request/{reqId}?brief=true` 폴링)이 구현되어 있습니다. 반면 UI(`ui/src/api/client.ts`)는 마이그레이션/NLB/데이터 전송에만 비동기 헤더를 사용하고 추천 API는 동기 방식으로 호출하고 있습니다.
- **개선안**: UI 및 외부 클라이언트에서 노드 수가 일정 임계치(예: `20대` 이상)이거나 전체 추천 호출 시 `Prefer: respond-async`를 기본 적용하고, 폴링 응답의 `subRequestSummary`(`total`, `success`)를 이용해 실시간 진행률을 표시하면 `20분`(`1,000대`) 이상 소요되는 추천도 타임아웃 없이 안정적으로 처리할 수 있습니다.

### 5.2 단일 요청 내 프로파일 메모이제이션 도입 (`O(N)` -> `O(고유 사양 수)`)

- **개선안**: `RecommendInfraCandidates` 실행 컨텍스트 내부에 요청 수명주기 동안만 유지되는 로컬 캐시 맵을 두어,
  1. 동일 `(Csp, Region, Architecture, vCPU, Memory, GPU)` 키에 대한 `RecommendNodeSpecs` 결과 재사용
  2. 동일 `(Csp, Region, Architecture, OS, GPU)` 키에 대한 `RecommendVmOsImages` 결과 재사용
  3. 동일 `(SpecId, ImageId, RootDiskType)` 조합에 대한 `PreflightCheckCspProvisioning` 결과 재사용
- **기대 효과**: `1,000대`(고유 프로파일 `12종`) 기준 하위 API 호출 수가 `5,000회 -> 약 60회 이내`로 **98% 이상 감소**하며, 소요 시간을 **`20분 13초`에서 `15~20초 이내`**로 단축할 수 있습니다(별도 캐시 무효화 이슈 없이 최신 카탈로그 정합성도 그대로 유지).

### 5.3 `lkvstore` 대규모 `SubRequests` 이력 경량화

- **개선안**: 단일 요청의 하위 호출(`SubRequests`) 개수가 임계치(예: `200개`)를 초과할 경우, `lkvstore` 영구 저장 시에는 집계 요약(`SubRequestSummary`)과 실패(`Error`) 항목만 보존하도록 제한하여 수천 대 이상 반복 수행 시의 인메모리 누적 및 스냅샷 파일 비대화를 방지합니다.
