## 1. Executive Summary & Purpose (배경 및 목적)

본 문서는 Cloud-Barista 클라우드 마이그레이션 생태계(Honeybee, Damselfly, Beetle, Tumblebug, UI) 전반에 걸쳐 **① ID 기반 경량 호출(Pass-by-Reference)**과 **② 마이그레이션 정보 및 모델 간의 유기적 파생 관계를 규정하는 Migration Lineage(마이그레이션 계보) 표준**을 수립하기 위한 전 서브시스템 공통 실행 계획입니다.

### 1.1 해결하고자 하는 문제 (Core Challenges)
1. **Pass-by-Value 오버헤드**: 수 MB에 달하는 모델 JSON 전체를 API 단계마다 주고받아 네트워크 낭비와 클라이언트 메모리 부하 발생.
2. **인과관계 단절**: 배포 완료된 클라우드 인프라(VM/NLB)를 보았을 때, 이것이 "과거 어떤 소스 서버로부터, 어떤 추천 계획을 거쳐 생성되었는지" 역추적할 수단 부재.
3. **레이블 불일치**: NodeGroup 생성 시 원본 머신 ID 레이블이 `sourceMachineId`(단수)와 `sourceMachineIds`(복수)로 파편화되어 리포트 및 감사 기능에 장애 유발.

### 1.2 목표 달성 방식 (Key Solutions)
- **최소 침습적 설계 (정보 및 모델 간의 관계 메타데이터)**: 인프라 기술 모델 자체(`OnpremInfra`, `RecommendedInfra`)의 내부 스키마를 오염시키지 않고, 정보 및 모델 간의 파생 관계를 규정하는 독립 메타데이터 레이어(Damselfly Model Envelope 및 Tumblebug Label)를 통해 완전한 계보 추적성을 성립.
- **단일 표준 및 No Fallback 원칙**: 침묵하는 폴백 부채를 방지하기 위해 `cm-source-machine-ids` 단일 표준 키를 확립하고, Grasshopper 팀에 사전 Breaking Change 공지.

## 2. 마이그레이션 라이프사이클과 3대 모델 + 리비전 체계

본 아키텍처는 모델 구조체를 불필요하게 늘리지 않고 기존 `OnpremInfra` 구조를 100% 재사용하며, 용어와 역할을 명확히 분리합니다:

```
[Phase 1: Discovery & Source Fact Registration]
  Honeybee Source Group (sourceGroupId: "sg-ecommerce-prod")
         │
         ▼ (Exported as Immutable Baseline)
  Damselfly Source Model (sourceModelId: "src-mdl-101", Read-Only Fact)
         │
[Phase 2: Planning & Modernization]
  Portal User clones Source Model and tunes OS/specs (CentOS 7 -> Ubuntu 22.04 LTS)
         │
         ▼ (Saved as Plan, Reusing OnpremInfra struct)
  Damselfly Planning Model (planningModelId: "plan-mdl-101", sourceModelId: "src-mdl-101")
         │
[Phase 3: Recommendation]
  Beetle Recommendation API Call: POST /recommendation/infra {"planningModelId": "plan-mdl-101"}
         │
         ▼ (Generated by Beetle Recommender)
  Damselfly Target Model v1.0 (targetModelId: "tgt-mdl-201", planningModelId: "plan-mdl-101", sourceModelId: "src-mdl-101")
         │ ├── NodeGroup 1 Label: {"cm-source-machine-ids": "srv-01,srv-02"}
         │ └── NodeGroup 2 Label: {"cm-source-machine-ids": "srv-03"}
         │
         ├─── (Optional: User adjusts CSP specs in Portal) ───┐
         │                                                    ▼
         │                                 Damselfly Target Model v1.1 (Revision)
         │                                 (isEdited: true, parentModelId: "tgt-mdl-201")
         ▼                                                    │
[Phase 4: Migration & Provisioning]                           │
  Beetle Migration API Call: POST /migration/infra ───────────┘
         │
         ▼ (Injected into Tumblebug InfraReq.Label & Sub-resources)
  Tumblebug Infra (infraId: "infra-prod-01")
         │ ├── Label["cm-target-model-id"]: "tgt-mdl-201"
         │ ├── Label["cm-planning-model-id"]: "plan-mdl-101"
         │ ├── Label["cm-source-model-id"]: "src-mdl-101"
         │ ├── Label["cm-source-group-id"]: "sg-ecommerce-prod"
         │ ├── Label["cm-migrated-at"]: "2026-09-30T10:30:00Z" (Runtime timestamp)
         │ └── NodeGroup / VM Level:
         │       └── Label["cm-source-machine-ids"]: "srv-01,srv-02"
         ▼ (Propagated to CSP Provider Tags)
  CSP Cloud Resources (AWS EC2 Tags / GCP Labels / Azure Tags)
```

## 3. 서브시스템 간 표준 협약 (Subsystem Interoperability Agreements)

### 3.1 레이블 표준화 정책: `cm-source-machine-ids` 단일화 (Breaking Change)
- **공식 단일 표준 키**: **`cm-source-machine-ids`**
  - 형식: 쉼표 구분 머신 ID 목록 (단일 머신인 경우 1개 ID)
  - 위치: 개별 노드/노드그룹(VM)의 `Label` 맵
  - 이유: NLB 백엔드 상향통합(`rightSizeUp`) 등으로 복수 서버가 단일 NodeGroup에 묶일 수 있으며, GCP 등 멀티클라우드 Label 규격(대문자 및 슬래시 금지)을 100% 만족함.
- **Breaking Change 정책**:
  - 침묵하는 폴백(Silent Fallback) 부채를 제거하기 위해 레거시 단수형 `sourceMachineId` 및 `sourceMachineIds`는 즉시 폐기하고 `cm-source-machine-ids`로 일원화함.
  - 관련 안내는 `docs/announcements/breaking-change-grasshopper.md` 공지 문서로 공유.

### 3.2 Tumblebug Infra 및 NodeGroup 레벨 레이블 규격

자원 단위(Granularity)와 생애주기(Lifecycle)에 맞추어 레이블을 계층별로 정의함:

#### 1) 인프라 최상위 레이블
| Label Key | Type | Description | Example |
| :--- | :--- | :--- | :--- |
| `cm-target-model-id` | `string` | 배포의 직접 청사진이 된 목표 모델 ID (v1.0 또는 v1.1) | `"tgt-mdl-20260930-001"` |
| `cm-planning-model-id` | `string` | 추천에 직접 사용된 마이그레이션 계획 모델 ID | `"plan-mdl-20260930-001"` |
| `cm-source-model-id` | `string` | 계획의 모체가 된 원천 소스 모델 ID (불변 팩트) | `"src-mdl-20260930-001"` |
| `cm-source-group-id` | `string` | 원천 Honeybee 소스 그룹 ID | `"sg-ecommerce-prod"` |
| `cm-migrated-at` | `string` | 프로비저닝 완료 UTC 일시 (ISO-8601, Beetle 배포 시점 생성) | `"2026-09-30T10:30:00Z"` |

#### 2) 개별 노드(NodeGroup / VM) 레벨 레이블
| Label Key | Type | Description | Example |
| :--- | :--- | :--- | :--- |
| `cm-source-machine-ids` | `string` | 매핑된 원천 머신 ID 목록 (쉼표 구분, Grasshopper 복제 대상) | `"srv-01,srv-02"` |

### 4.2 CM-Damselfly 업데이트 요청 명세서 (Request Spec to Damselfly Team)

Damselfly 팀에 모델 스키마 및 저장 규격에 대한 아래 3가지 확장을 요청합니다:

#### 1) 소스 모델 (Source Model: 불변 원천 팩트)
* **API**: `POST /damselfly/infra-model?modelType=source`
* **요청 본문 및 응답 Envelope**:
  ```json
  {
    "id": "src-mdl-20260930-001",
    "name": "Onprem Web Cluster (Original)",
    "modelType": "source",
    "lineage": {
      "sourceGroupId": "sg-ecommerce-prod",
      "sourceModelId": "src-mdl-20260930-001"
    },
    "description": "Immutable source fact from Honeybee",
    "onpremiseInfraModel": { ... }
  }
  ```

#### 2) 계획 모델 (Planning Model: 사용자가 OS/스펙을 조율한 계획, 구조체 100% 재사용)
* **API**: `POST /damselfly/infra-model?modelType=planning`
* **요청 본문 및 응답 Envelope**:
  ```json
  {
    "id": "plan-mdl-20260930-001",
    "name": "E-Commerce Cloud Migration Plan",
    "modelType": "planning",
    "lineage": {
      "sourceGroupId": "sg-ecommerce-prod",
      "sourceModelId": "src-mdl-20260930-001",
      "planningModelId": "plan-mdl-20260930-001"
    },
    "description": "User tuned modernization plan (CentOS -> Ubuntu 22.04 LTS)",
    "onpremiseInfraModel": { ... }
  }
  ```
  *(주: 페이로드는 신규 구조체 없이 기존 `OnpremInfra`를 그대로 재사용)*

#### 3) 목표 모델 (Target Model: 추천 결과 및 사용자 리비전)
* **API**: `POST /damselfly/infra-model?modelType=target`
* **요청 본문 및 응답 Envelope**:
  ```json
  {
    "id": "tgt-mdl-20260930-001",
    "name": "Recommended AWS Infra",
    "modelType": "target",
    "lineage": {
      "sourceGroupId": "sg-ecommerce-prod",
      "sourceModelId": "src-mdl-20260930-001",
  ```

## 5. 공지 템플릿 (Subsystem Announcement Draft)

전체 서브시스템(슬랙 채널, 이슈 트래커, 주간 싱크) 공유용 공지문 초안:

```markdown
[공지] 클라우드 마이그레이션 Lineage 추적성 및 3대 모델 생애주기 표준화 안내

Cloud-Barista 마이그레이션 파이프라인의 효율성과 추적성을 강화하기 위해,
Beetle-Damselfly-Honeybee-UI 간 모델 생애주기 및 연관관계 규격이 아래와 같이 표준화됩니다.

1. 주요 개선 사항
   - 3대 모델 생애주기 정립:
     * Source Model (원천 온프레미스 팩트, 수정 금지)
     * Planning Model (사용자 전환 계획, OnpremInfra 구조 재사용, 자유 수정)
     * Target Model (추천 목표 설계도 및 사용자 리비전)
   - ID 기반 경량 호출: 거대 JSON 대신 modelId 전달을 통한 대역폭 및 성능 최적화
   - 엔드-투-엔드 계보 추적: 생성된 클라우드 인프라의 태그/Label에서 원천/계획/목표 모델 ID 즉시 역추적 가능

2. Label 키 표준화 (Breaking Change)
   - 공식 단일 표준 키: `cm-source-machine-ids`
   - 사유: 복수 머신 그룹핑 지원 및 GCP 등 CSP 규격 준수 (소문자/하이픈)
   - 레거시 단수형 키(`sourceMachineId`)는 침묵하는 폴백 부채를 방지하기 위해 단일 표준으로 일원화

3. 서브시스템별 조치 요청
   - Damselfly: 모델 Envelope에 `lineage` 메타데이터 필드 반영
   - Grasshopper: Node Label 참조 시 `cm-source-machine-ids` 단일 키 참조
   - Beetle: 추천/마이그레이션 DTO에 `lineage` 지원 및 Tumblebug Label 주입
   - UI: [SourceInfraRefinement]에서 Planning Model 저장 지원 및 인프라 관리 화면에서 출처 모델 ID 뱃지 표시

상세 설계는 `docs/plan/lineage-plan.md` 및 `docs/announcements/` 문서를 참고해 주시기 바랍니다.
```

## 6. 단계별 점진적 릴리스 로드맵 (Phased Roadmap)

1. **Phase 1 (Beetle 계보 표준 패키지 및 Label 키 표준화)**:
   - `imdl/lineage` 독립 패키지 도입 및 `cm-source-machine-ids` 단일 표준 적용.
   - 마이그레이션 실행 시 배포 일시(`cm-migrated-at`) 및 계보 Label 주입.
2. **Phase 2 (Damselfly 필드 확장 & 연동)**:
   - Damselfly 모델 Envelope에 `lineage` 메타데이터 필드 반영.
3. **Phase 3 (Grasshopper 단일 표준 Label 연계 & UI 시각화)**:
   - Grasshopper에서 `cm-source-machine-ids` 참조 및 데이터 복제 1:1 인덱스 매핑.
   - UI에서 계보 모델 정보 및 리포트 렌더링.
